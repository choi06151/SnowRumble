# Task Writing

## 목적

이 문서는 4인 역할별 Task 문서를 작성하거나 구현 후 갱신할 때 따르는 규칙입니다.

## 기준 원본

- 역할 내부 우선순위와 상태: `Tasks/{코드}/PLAN_{코드}.md`
- 파트 간 필수 의존성·공용 계약·선점과 통합 상태: `docs/PLANS.md`
- 역할·소유권·충돌 대응: `docs/COLLABORATION.md`
- 기능 경계와 의존 방향: `docs/ARCHITECTURE.md`
- 코드·자산 작성 기준: `docs/STYLEGUIDE.md`
- 구현·승인·상태 전이: `docs/WORKFLOW.md`

역할 문서와 Task는 위 규칙을 복사하지 않고 현재 작업에 필요한 실제 범위와 인계만 기록합니다.

## 역할별 구조

```text
Tasks/
├─ C/                    # 최재원, 메인 프로그래머
│  ├─ ROLE_C.md
│  ├─ PLAN_C.md
│  └─ C-XX_*.md
├─ K/                    # 강혜원, 서브 프로그래머
│  ├─ ROLE_K.md
│  ├─ PLAN_K.md
│  └─ K-XX_*.md
├─ S/                    # 서유정, UI·아트·레벨
│  ├─ ROLE_S.md
│  ├─ PLAN_S.md
│  └─ S-XX_*.md
└─ J/                    # 정다영, 레벨
   ├─ ROLE_J.md
   ├─ PLAN_J.md
   └─ J-XX_*.md
```

- 각 담당자는 자기 `ROLE_*.md`, `PLAN_*.md`, 현재 Task와 직접 연결된 선행 Task만 읽습니다.
- 역할 내부 상태와 우선순위는 `PLAN_*.md`에서 갱신합니다.
- `docs/PLANS.md`에는 역할 내부 세부 순서를 복사하지 않고 파트 간 필수 의존성·공용 계약·선점과 통합 상태만 기록합니다.
- 기존 루트 `Tasks/*.md`와 `S*.md`는 구조 개편 전 이력으로 보존합니다.

## 파일명과 제목

- 파일명: `{담당자 코드}-{두 자리 번호}_{영문 설명}.md`
- 예: `C-03_random_team_lobby.md`, `K-02_gift_box.md`, `S-05_overhead_nameplate.md`, `J-01_ice_glacier_blockout.md`
- 영문 설명은 소문자와 언더스코어만 사용합니다.
- 제목: `# Task {담당자 코드}-{번호} - {기능명}`
- 역할 문서: `ROLE_C.md`, `ROLE_K.md`, `ROLE_S.md`, `ROLE_J.md`
- Task와 기준 문서는 파일명 담당자 이니셜 접미사 규칙의 예외입니다.
- Task 번호는 생성 순서에 따른 고정 식별자이며 실행 순서를 뜻하지 않습니다.
- 우선순위가 바뀌어도 Task 파일 이름과 ID를 변경하지 않습니다.

## 기본 원칙

- Task는 한 담당자가 한 번에 구현하고 검증할 수 있는 결과 단위로 작성합니다.
- 구현 전에는 What, 즉 필요한 결과와 계약만 적고 내부 함수·파일 분리 방식을 추측하지 않습니다.
- 사용자가 구현 방식을 직접 결정했다면 해당 How는 그대로 반영할 수 있습니다.
- GDD의 미결정 사항이 필요한 Task는 `결정 필요`에 기록하고 확정 전 구현하지 않습니다.
- 범위 밖 결과를 Task에 임의로 추가하지 않습니다.
- 새 Task를 만들면 해당 역할 `PLAN_*.md`에 추가합니다. 다른 역할의 계약·선점·통합 순서에 영향이 있을 때만 메인 프로그래머가 `docs/PLANS.md`도 갱신합니다.

## 대화 기반 자율 계획

- 개발자는 `PLAN_*.md`나 Task 문서를 직접 작성할 필요가 없습니다.
- 개발자가 원하는 결과, 오류, 불편한 점, 우선순위 변경이나 중단 요청을 말하면 현재 담당자의 Codex가 관련 GDD·소유권·의존성을 확인해 문서를 갱신합니다.
- Codex는 대화에서 합의된 내용을 Task 추가·분할·순서 변경·상태 변경으로 변환하고 변경 요약을 사용자에게 알려줍니다.
- 결과와 범위가 명확한 역할 내부 변경은 Codex가 합리적으로 분류해 진행할 수 있습니다.
- GDD 결과, 공용 계약, 다른 역할 소유권이나 전체 통합 순서가 바뀌면 임의로 확정하지 않고 메인 프로그래머에게 `통합 변경 요청`으로 인계합니다.

## 최초 개발 스타일 반영

- 각 담당자가 자기 역할의 최초 Task를 시작하려 할 때, Codex는 구현 승인 요청 전에 개발 스타일을 먼저 확인합니다.
- 확인할 개발 스타일은 최소 아래 세 가지 중 하나입니다.
  - Blueprint 위주: C++는 필요한 부모 클래스·공용 계약·검증 지점만 두고 에디터 자산과 Blueprint 작업을 중심으로 진행합니다.
  - C++ 위주: 서버 권한, 상태, 수명주기와 검증 로직을 C++ 중심으로 두고 Blueprint는 표현·배치·조정값 연결에 집중합니다.
  - 혼합: 안정적인 서버 판정과 반복 로직은 C++로 두고, 표현·맵 배치·UI 흐름은 Blueprint와 에디터 작업으로 나눕니다.
- 개발 스타일을 확인한 뒤 Codex는 현재 담당자의 `PLAN_*.md`와 Task 목록을 사용자에게 요약해 보여주고, 현재 순서가 그 스타일에 맞는지 확인합니다.
- 사용자가 선호 스타일이나 순서를 말하면 Codex가 해당 역할의 `PLAN_*.md`와 필요한 Task 문서를 먼저 조정합니다.
- 이 조정은 MVP 결과를 바꾸지 않는 한 역할 내부 자율 계획으로 처리할 수 있습니다.
- 공용 계약, 다른 역할 소유권, 중앙 의존성이나 병합 순서가 바뀌면 `docs/COLLABORATION.md`와 `docs/PLANS.md` 기준으로 C 통합 경로를 사용합니다.
- 개발 스타일은 코드 품질 기준을 낮추는 예외가 아닙니다. Blueprint 위주여도 서버 권한·복제 원본·공용 상태는 정해진 소유자가 관리합니다.

### 역할 내부에서 자율적으로 가능한 변경

- 자기 `PLAN_*.md`의 Task 우선순위 변경
- 자기 소유 파일·자산만 사용하는 Task 추가·분할
- 완료 조건을 바꾸지 않는 오류 수정 항목 추가
- 계약 없이 가능한 조사·레이아웃·모델·블록아웃 작업 전환
- 선행 계약을 기다리는 Task를 `대기`로 두고 다른 시작 가능 Task 선택

### 통합 변경 요청이 필요한 변경

- GDD의 기대 결과나 MVP 범위 변경
- 공용 API·이벤트·복제 상태의 추가·변경
- 다른 역할의 파일·자산·Task 순서 변경
- `.uasset`·`.umap` 소유자 변경
- 파트 간 필수 선행 관계와 최종 병합 순서 변경

비메인 담당자의 Codex는 필요한 내용을 자기 `PLAN_*.md`의 `통합 변경 요청`에 기록합니다. 최재원(C) Codex가 이를 검토해 공용 문서와 중앙 `docs/PLANS.md`를 갱신합니다.

## Task 변경과 오류 대응

- 현재 완료 조건 안에서 고칠 수 있는 오류는 현재 Task의 구현 항목에 추가합니다.
- 독립적으로 구현·검증할 수 있거나 현재 Task를 과도하게 키우는 오류는 다음 사용 가능한 고정 ID로 새 Task를 만듭니다.
- 다른 파트 계약이 없어서 진행할 수 없으면 현재 Task를 `대기`로 바꾸고 통합 변경 요청을 기록합니다.
- 기존 범위를 다른 Task가 대신하면 원래 Task를 `대체`로 표시하고 대체 Task 링크를 남깁니다.
- 완료된 Task에서 수정이 필요하면 기존 완료 이력을 보존한 채 `진행중`으로 되돌리거나 독립 수정 Task를 만듭니다.
- Task를 분할하거나 대체하더라도 기존 파일을 삭제하거나 번호를 재사용하지 않습니다.

## 역할 계획 상태

- `예정`: 아직 시작하지 않았거나 우선순위가 오지 않은 상태
- `진행중`: 현재 구현 또는 결과 확인 중인 상태
- `대기`: 사용자 결정·외부 계약·오류 해결을 기다리는 상태
- `완료`: 구현·인계·결과 확인이 끝난 상태
- `대체`: 다른 Task로 범위를 옮겨 직접 진행하지 않는 상태

- 한 담당자는 기본적으로 구현 Task 하나만 `진행중`으로 둡니다.
- 서로 다른 파일을 사용하는 조사·블록아웃·긴급 수정은 충돌 없음이 기록된 경우 병행할 수 있습니다.

## 필수 섹션

모든 새 역할별 Task에는 아래 항목을 둡니다.

- 설명
- 상태 전이 기준
- 구현 항목
- 작업 배정
- 공용 계약과 인계
- 범위 밖
- 사전 전제 또는 결정 필요
- 수동 작업
- 완료 조건

`작업 배정`에는 담당자, 기능 소유자, 계약 소유자, 자산 수정자, 선점 대상, 공유 확인 대상과 병합 순서를 기록합니다.

## 작성 시점별 규칙

### 구현 전

- `구현 항목`에는 현재 Task에서 달성해야 하는 결과만 적습니다.
- 생성·변경 파일과 자산은 조사 전 추측하지 않고 `구현 승인 전 확정`으로 둡니다.
- 다른 역할의 결과가 필요하면 실제 선행 Task를 연결합니다.
- 공개 계약에는 필요한 데이터·요청·이벤트와 실행 위치 결과만 적습니다.
- 존재하지 않는 클래스·함수·이벤트·프로퍼티 이름을 추측하지 않습니다.
- `수동 작업`과 `결과 확인`은 실제 구현 전에는 구체화하지 않습니다.
- 한 Task가 서로 독립적으로 검증할 동작을 여러 개 포함하면 분리합니다.

### 구현 후

- 실제 추가·변경된 파일, 클래스, 함수, 이벤트, Blueprint와 자산 이름으로 갱신합니다.
- 완료한 구현·에이전트 확인만 `[x]`로 표시합니다.
- 공개 계약의 호출 조건, 실행 위치와 소비 파트를 실제 결과로 기록합니다.
- 담당자가 에디터에서 해야 할 저장 작업은 `수동 작업`에 구체화합니다.
- 실행과 관찰 절차는 `결과 확인`에 구체화합니다.
- 사용자가 수동 작업과 결과 확인 완료를 응답하기 전에는 완료 처리하지 않습니다.

## 파트 간 인계

- 제공자 Task와 소비자 Task를 모두 기록합니다.
- 계약 제공 Task가 완료되기 전 소비자 Task는 구현을 시작하지 않습니다.
- UI·모델·레벨처럼 계약 없이 병렬 진행 가능한 작업은 레이아웃, 블록아웃, 원본 제작 범위만 진행합니다.
- 다른 역할 파일을 변경해야 하면 Task 범위를 늘리지 않고 계약 소유자에게 반환합니다.
- 인계 형식은 `docs/COLLABORATION.md`를 따릅니다.

## 수동 작업과 결과 확인

- 프로젝트에 변경을 남기는 에디터 입력·연결·설정·배치는 `수동 작업`에 적습니다.
- 아무것도 바꾸지 않고 실행하거나 관찰하는 절차는 `결과 확인`에 적습니다.
- 두 섹션에 같은 절차를 반복하지 않습니다.
- 초보자가 그대로 따라 할 수 있게 실제 이름과 순서로 작성합니다.

## 기존 Task 처리

- 기존 Task 문서는 당시 구현·검증 이력으로 유지하며 새 문서로 덮어쓰지 않습니다.
- 새 기획과 역할 구조에 따른 분류는 `Tasks/LEGACY_MIGRATION.md`에서 관리합니다.
- 기존 Task의 완료 표시는 새 기획에 대한 완료를 의미하지 않습니다.
- 재사용하는 구현은 새 Task에서 `유지` 또는 `재검증` 대상으로 연결합니다.
