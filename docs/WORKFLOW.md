# Workflow

## 목적

이 문서는 AI 에이전트가 task를 진행할 때 따라야 할 작업 순서, 진행 제약, 상태 관리 규칙을 정의합니다.

## 적용 범위

- 이 문서의 `작업 흐름`은 이미 생성된 task 문서를 기준으로 해당 task를 처음 구현 시작할 때만 적용합니다.
- 새 task 문서를 생성하거나 초안을 작성할 때는 이 문서의 `작업 흐름`을 적용하지 않습니다.
- 같은 task를 한 번 진행한 뒤, 이후 멀티턴으로 수정 사항을 반영할 때는 전체 `작업 흐름`을 반복하지 않고, 작업 흐름의 1, 4, 8~10과 12~14의 확인·기록 단계를 기준으로 진행합니다. 
- 이미 `완료`된 task에 수정 요청이 오면 해당 역할 `PLAN_*.md`의 상태를 `진행중`으로 되돌리거나 독립 수정 Task를 만들고, 결과 확인이 끝나면 다시 `완료`로 갱신합니다.
- 다만 새 파일 생성, 구조 변경, 에디터 자산 작업, 또는 최초 합의 범위를 넘는 변경이 생기면 6, 7을 다시 진행하고, 구현 후에는 11의 의심 정리도 함께 진행합니다.
<!-- 유지보수 주의: 이 섹션의 "1, 4, 8~10", "12~14", "6, 7", "11"은 아래 작업 흐름의 단계 번호 참조라서, 작업 흐름에 단계를 삽입·삭제·재배열하면 이 번호들도 함께 갱신해야 한다. -->

여러 담당자가 함께 작업할 때 역할, 기능·계약·자산 소유권과 충돌 대응은 `docs/COLLABORATION.md`를 함께 적용합니다.


## 문서 우선순위

문서 해석 우선순위는 아래와 같습니다.

1. 사용자 직접 요청
2. 현재 진행 중인 task 문서
3. `docs/WORKFLOW.md`
4. 현재 담당자의 `PLAN_*.md`
5. `docs/PLANS.md`
6. 나머지 프로젝트 문서

`docs/HARNESS.md`는 규칙 운영 절차를 다루는 메타 문서라 위 우선순위의 경쟁 대상이 아니며, 규칙 추가·조정·이탈 대응은 항상 HARNESS.md의 절차를 따릅니다.

아래 `진행 제약`은 task 문서를 포함한 어떤 문서도 덮어쓰지 못합니다. 사용자 직접 요청은 범위와 승인 제약을 조정할 수 있지만, 비밀값의 출력·기록 금지는 어떤 경우에도 변하지 않습니다.

문서끼리 충돌하거나 현재 저장소 상태와 맞지 않으면, 구현 전에 불일치를 먼저 보고하고 수정 범위를 제안합니다.

## 멀티플레이 기능 추가 절차

멀티플레이가 관련된 Task는 일반 작업 흐름과 함께 아래 절차를 적용합니다.

1. 한 번에 구현하고 검증할 동작 하나를 선택합니다. 현재 Task가 여러 네트워크 동작을 포함하면 먼저 검증 가능한 단위로 나눌지 사용자에게 제안합니다.
2. 구현 전에 선택한 동작을 아래 네 책임으로 구분해 사용자에게 설명합니다.
   - 소유 클라이언트가 받는 입력과 로컬 전용 처리
   - 서버가 검사하고 확정하는 게임 규칙
   - 다른 참가자에게 복제해야 하는 상태와 결과
   - Blueprint에서 연결할 모델, 애니메이션, UI, 이펙트, 사운드, 조정값
3. C++는 현재 동작에 필요한 서버 권한·RPC·복제 기본틀과 Blueprint 연결 지점까지만 구현합니다.
4. 구현 후 현재 Task 문서의 `수동 작업`에 개발자가 Blueprint에서 완성할 절차를 실제 클래스·함수·이벤트·프로퍼티 이름 기준으로 작성합니다.
5. `결과 확인`에는 호스트가 행동한 경우와 클라이언트가 행동한 경우를 모두 포함하고, 각 화면에서 필요한 상태가 동일하게 보이는지 확인하게 합니다.

이 절차는 멀티플레이 구조를 설명하기 위한 것이며, 사용자가 요청하지 않은 완성형 Blueprint 자산이나 최종 연출을 코드로 대신 생성하는 근거가 되지 않습니다.

## 파트 간 계약과 인계

1. 선행 계약 Task와 이를 사용하는 기능·자산 Task는 별도 문서와 별도 상태로 관리합니다.
2. 계약 소유자는 다른 파트가 사용할 실제 데이터, 함수와 이벤트를 먼저 완성합니다.
3. 인계에는 실제 클래스·함수·이벤트·프로퍼티 이름, 호출 조건과 실행 위치를 기록합니다.
4. 기능 담당자는 필요한 선행 계약이 완료되고 인계 정보가 기록된 후 연결 작업을 시작합니다.
5. UI·레벨·아이템은 다른 파트가 소유한 서버 판정이나 복제 상태를 직접 변경하지 않습니다.
6. 필요한 계약이 부족하면 다른 파트의 파일을 직접 수정하지 않고 `docs/COLLABORATION.md`의 공용 계약 변경 절차를 사용합니다.
7. 선행 계약 Task 완료는 이를 사용하는 후속 Task 완료를 의미하지 않으며 상태를 따로 갱신합니다.

## 작업 흐름

이미 생성된 task 문서를 기준으로 해당 task를 처음 구현 시작할 때, 아래 순서로 작업합니다.
아래 순서는 형식적으로 진행하지 않으며, 각 단계를 건너뛰지 않고 실제로 수행합니다.

1. 관련 task와 선행 산출물을 확인합니다.
2. 현재 담당자의 `PLAN_*.md`에서 우선순위·필수 선행과 상태를 확인하고 작업 시작 시 `진행중`으로 갱신합니다. 공용 계약·선점이나 파트 간 통합 영향은 `docs/PLANS.md`도 확인합니다.
3. `docs/ARCHITECTURE.md`의 내용을 모른다면 확인합니다.
4. 관련 코드와 현재 맵, Blueprint, 자산 구조를 읽습니다. 관련 코드가 아직 없으면 이 단계는 건너뜁니다.
5. `docs/STYLEGUIDE.md`의 내용을 모른다면 확인합니다.
   - 특히 구현 방식과 승인 요청 작성 전에 `Unreal Editor 작업 규칙`을 기준으로 판단해야 한다.
6. 아래 항목들을 보수적으로 판단하며, 하나라도 해당되거나 조금이라도 의심되면 `책임 범위 의심 파일`에 기재합니다. 기재는 분리가 필요하다는 판단과는 별개입니다.
    - 같은 성격의 내용이 여러 파일에 반복되는지
    - 공통화 가능성이 조금이라도 있는지
    - 추가할 코드의 성격이 대상 파일의 현재 책임 범위와 다른지
    - 다른 프로그래머가 선점했거나 수정 중인 파일·자산과 겹치는지
    
7. 구현 전 반드시 아래 `구현 진행 승인 요청` 섹션의 형식으로 승인 요청을 출력하고, 사용자 승인을 받은 뒤 다음 단계로 넘어갑니다.
8. 필요한 코드 변경을 구현합니다.
9. `docs/TESTING.md`의 현재 실행 확인 모드에 따라 확인을 진행합니다.
10. 구현 후 `docs/TASK_WRITING.md`의 작성 규칙에 맞춰 task 문서를 실제 코드 기준으로 갱신합니다.
11. 구현 전 승인 요청의 `책임 범위 의심 파일`은 구현 후 상태에 따라 `Pending Issues 관리` 규칙에 맞게 정리합니다.
12. 사용자에게 필요한 수동 작업 또는 결과 확인을 요청합니다.
13. 결과 확인이 끝나면 아래 `작업 로그 관리` 규칙에 따라 로그를 정리합니다.
14. 확인이 완료된 뒤 task 문서와 현재 담당자의 `PLAN_*.md`에서 상태를 `완료`로 갱신합니다. 공용 계약·선점·통합 관문이 바뀌면 최재원(C) Codex가 `docs/PLANS.md`도 갱신합니다.

## 구현 진행 승인 요청

구현 전 승인 요청은 반드시 아래 형식으로 출력합니다.

**[구현 진행 승인 요청]**
- 현재 Codex 담당자:
- 기능 소유자:
- 계약 소유자:
- 자산 수정자:
- 생성 후보 파일:
- 변경 후보 파일:
- 변경 요약:
- 작업 역할: 서유정(S) / 정다영(J) / 강혜원(K) / 최재원(C)
- 선점 파일·자산:
- 공유 확인 대상:
- 인계 조건:
- 공용 계약 변경 여부: 있음(대상 API·이벤트·복제 상태와 영향받는 파트) / 없음
- 에디터 자산 필요 여부: 있음(어떤 자산인지) / 없음
- 멀티플레이 적용 여부: 적용(아래 네트워크 항목 작성) / 비적용
- 네트워크 흐름: (적용 시 소유 클라이언트 입력 → 서버 검사·확정 → 복제 결과 순서)
- C++ 책임: (적용 시 서버 권한·RPC·복제·Blueprint 연결 지점 중 이번 구현 범위)
- Blueprint 책임: (적용 시 사용자가 에디터에서 완성할 표현·자산 연결·조정값)
- 책임 범위 의심 파일: (조금이라도 의심되면 기재, 분리 여부는 사용자가 결정, 의심이 전혀 없으면 "없음")
- 의심 사유: (없으면 "없음")
- 의심에 대한 제안 : (의심 파일마다 분리안과 기존 파일 유지안을 각각 설명하고 사용자가 선택하게 한다. 이 항목 작성이 의심 해소를 뜻하지 않는다.)
- 의심에 대한 추천 진행 : (분리안/유지안, 간단한 이유)
- 사용자 승인 전 구현 안 함

## 진행 제약

- 구현은 task 구현 항목에 명시된 것만 합니다. 범위 밖 항목은 구현하지 않습니다.
- 범위 밖 작업이 필요해지면(새 폴더, 새 플러그인, 새 모듈, 대규모 리팩터링, 대규모 에셋 구조 변경 등) 이유와 범위를 사용자에게 알리고 승인을 받은 뒤 진행합니다.
- 다른 프로그래머의 전용 범위나 선점 대상을 수정해야 하면 `docs/COLLABORATION.md`에 따라 메인 프로그래머가 재배정하기 전까지 수정하지 않습니다.
- 프로젝트 내 민감한 계정 정보, API 키, 인증 토큰, 비밀값은 기본적으로 읽지 않습니다. 사용자가 명시적으로 요청한 경우에만 필요 최소한으로 접근하되, 어떤 경우에도 출력하거나 코드·문서·로그·커밋에 적지 않습니다.
- `Config/`와 환경 설정을 점검할 때는 파일 전체를 먼저 출력하지 않습니다. `Token`, `Key`, `Secret`, `Password`처럼 민감할 수 있는 키의 존재를 값 없이 먼저 확인하고, 해당 파일은 필요한 비민감 구간만 조회합니다.
- 민감 키 존재 여부를 확인할 때는 일치한 줄 내용을 출력하는 `rg`, `Select-String` 또는 문자열 치환 출력을 사용하지 않습니다. 검사 결과는 파일명과 발견 여부 또는 개수만 반환하고, 값과 해당 줄의 나머지 내용은 출력하지 않습니다.
- 결과 확인이 끝나기 전에는 다음 단계로 넘어가지 않습니다.
- 구현과 문서 갱신은 같은 작업 흐름 안에서 함께 반영합니다.

## 상태 관리 원칙
- 역할 내부 구현, 실행 확인과 결과 확인 결과는 해당 `PLAN_*.md`와 Task의 변경 기록에 남깁니다.
- 파트 간 계약·선점·병합·통합 결과만 `docs/PLANS.md`의 최근 통합 로그에 남깁니다.
- 사용자 결정이나 외부 계약이 없어 진행할 수 없으면 `대기`로 바꾸고 이유와 재개 조건을 기록한 뒤 시작 가능한 다른 Task를 선택할 수 있습니다.
- 다른 역할에 영향이 있는 대기 원인은 자기 계획의 `통합 변경 요청`에 기록합니다.
- `PLAN_*.md`, `docs/PLANS.md`, `docs/LOGS.md`, `docs/PENDING_ISSUES.md` 같은 기록 문서의 운영 규칙은 이 문서를 기준으로 관리합니다.

## Pending Issues 관리
- 해소되지 않은 의심은 `docs/PENDING_ISSUES.md`에 기록합니다.
- 이번 작업에서 기존 구조를 유지하기로 했더라도, 그 결정이 의심 해소를 뜻하지 않으면 `해소되지 않은 의심`으로 보고 `docs/PENDING_ISSUES.md`에 기록합니다.
- 같은 파일과 같은 성격의 의심은 중복으로 추가하지 않습니다.
- 실제로 해소된 항목은 `docs/PENDING_ISSUES.md`에서 제거합니다.

## 작업 로그 관리

- 각 `PLAN_*.md`의 `계획 변경 기록`은 해당 역할의 최신 Task 변화 확인용으로 유지합니다.
- `docs/PLANS.md`의 `최근 통합 로그`는 파트 간 최신 진행 상황 확인용으로 유지합니다.
- `docs/PLANS.md`의 `최근 통합 로그`가 20줄 이상이 되면 최재원(C) Codex는 가장 오래된 15줄을 `docs/LOGS.md`로 이동하고 최신 5줄만 남깁니다.
- 이동한 로그는 삭제하지 않고 `docs/LOGS.md`에 유지합니다.
