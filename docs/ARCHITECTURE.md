# Architecture

## 목적
이 문서는 AI 에이전트가 파일을 만들거나 이동할 때 폴더 책임, 파일 배치, Unreal 자산 배치 규칙을 확인하는 기준 문서입니다.

## 구조 원칙

- Unreal C++ 코드, Blueprint 자산, 맵, 문서 책임을 분리합니다.
- 지금 필요한 범위에서만 구조를 확장합니다.
- 파일과 자산의 이름 규칙은 `docs/STYLEGUIDE.md`의 `이름 규칙`을 따릅니다.
- 기능의 내부 구현과 다른 파트가 사용할 공개 계약을 분리합니다.
- 경기 상태의 원본은 한 시스템만 소유하며 UI·레벨·아이템이 같은 상태를 중복 보관하거나 판정하지 않습니다.
- 담당자와 현재 수정자는 `docs/COLLABORATION.md`의 기능·계약·자산 소유권으로 관리합니다.

## 기능 경계와 의존 방향

### 공용 경기 계약

- 세션, 팀, 라운드, 매치, 승패와 공용 플레이어 상태의 서버 권한 계약을 제공합니다.
- 공용 계약은 UI나 특정 맵의 내부 자산에 의존하지 않습니다.
- 여러 파트가 사용하는 API를 변경할 때는 `docs/COLLABORATION.md`의 공용 계약 변경 절차를 따릅니다.

### 플레이어와 PvP

- 플레이어 입력과 기능 연결, 공용 플레이어 상태, PvP 흐름을 소유합니다.
- 아이템·맵·UI가 사용할 검증된 요청 함수와 읽기 전용 상태·이벤트를 제공합니다.
- 특정 아이템, 특정 맵 또는 특정 Widget의 내부 구현에 직접 의존하지 않습니다.

### 아이템

- 아이템 생성, 획득, 소유, 사용, 수명주기와 개별 효과를 내부에 캡슐화합니다.
- 플레이어 HP나 경기 결과를 직접 덮어쓰지 않고 공용 플레이어·경기 계약을 사용합니다.
- 모델·머티리얼 같은 표현 자산은 에디터에서 연결하고 아이템 로직의 원본 상태를 갖지 않습니다.

### 레벨과 맵 환경

- 맵별 배치, 동선, 환경 위험과 공간 변화를 담당 맵 내부에 둡니다.
- 주요 게임 규칙을 Level Blueprint에 집중하지 않고 재사용 가능한 전용 Actor 또는 Component로 구성합니다.
- 플레이어 피해와 경기 단계 변경은 공개된 서버 요청 계약을 사용합니다.
- 하나의 `.umap`에는 한 시점에 한 명의 자산 수정자만 둡니다.

### UI와 표현 자산

- UI는 공개된 읽기 전용 상태와 이벤트를 사용하고, 필요한 행동은 검증된 요청 함수로 전달합니다.
- UI에서 팀, 피해, 아이템 보상, 얼기, 승패를 별도로 판정하지 않습니다.
- 모델, 애니메이션, VFX, 사운드와 머티리얼은 게임 상태의 원본을 소유하지 않습니다.

### 허용 의존 방향

```text
UI·표현 ────────> 공개 읽기 상태·이벤트
아이템 ─────────> 공용 플레이어·경기 요청 계약
맵 환경 ────────> 공용 플레이어·경기 요청 계약
플레이어·PvP ───> 공용 경기 계약
```

- 화살표의 반대 방향으로 구체 구현을 직접 참조하지 않습니다.
- 양방향 연결이 필요하면 한쪽의 내부 변수를 공개하는 대신 인터페이스, 델리게이트 또는 소유자가 제공한 요청 함수를 사용합니다.
- 실제 사용처가 하나뿐이고 변경 가능성도 확인되지 않은 기능에 범용 프레임워크를 미리 만들지는 않습니다.

## 캡슐화 단위

- 상태와 상태를 변경하는 규칙을 같은 Actor, Component 또는 시스템이 소유합니다.
- 독립적인 상태·수명주기·복제 책임이 생긴 기능은 기존 대형 클래스에 계속 추가하지 않고 Component 또는 전용 Actor 분리를 검토합니다.
- 단순 연결 함수만 있는 작은 동작을 이유로 파일과 컴포넌트를 과도하게 분리하지 않습니다.
- 조정값은 실제 사용하는 소유 시스템 한 곳에 두고 여러 Blueprint에 같은 값을 복사하지 않습니다.
- 외부 파트는 내부 구현이 바뀌어도 공개 계약이 유지되는 한 수정하지 않아도 되는 구조를 목표로 합니다.

## 공통 폴더 책임

- `.agents/skills/`: 저장소의 모든 담당자 Codex가 공유하는 실행 Skill
- `docs/`: 하네스 문서와 작업 규칙
- `Tasks/`: 개별 task 문서
- `Source/`: C++ 코드
- `Content/`: Blueprint, 맵, 애니메이션, 모델, 머티리얼 등 Unreal 자산

## 향후 자산 배치 기준

- 캐릭터, 상호작용 대상, 게임 규칙 등 C++ 구현은 `Source/SnowRumble/` 아래에서 책임별로 분리합니다.
- Blueprint와 맵은 `Content/` 아래에서 역할별 폴더를 만들되, 해당 자산이 필요한 Task에서 실제 구조를 확정합니다.
- UI, 모델과 맵 자산은 실제 첫 역할별 Task에서 `Content/` 아래 책임 폴더와 단독 수정자를 확정하며 서로 다른 책임의 자산을 무분별하게 섞지 않습니다.
- 네트워크 복제 대상과 로컬 전용 표현 자산의 책임을 구분합니다.
- GDD의 장기 기능만을 이유로 미리 코드 폴더나 빈 자산 폴더를 만들지 않습니다.
- 역할별 Task 폴더는 확정됐지만 새 코드·자산 폴더는 첫 실제 Task에서 기능·계약·자산 소유권과 의존 방향을 확인한 뒤 생성합니다.

## 권장 파일 배치

- 파일은 먼저 `## 현재 프로젝트 폴더 책임과 구조`에 기록된 폴더 책임을 기준으로 배치합니다.
- 같은 성격의 파일은 기존에 정의된 책임 폴더를 우선 재사용합니다.

## 변경 원칙

- 파일이 기존에 정의된 책임 폴더로 배치할 수 없으면 새 폴더를 생성한 뒤 배치합니다.
- 새 폴더, 새 플러그인, 새 모듈, 대규모 리팩터링 같은 task 범위 밖 변경의 금지와 승인 절차는 `docs/WORKFLOW.md`의 `진행 제약`을 따릅니다.
- 새 폴더를 생성하면 `## 현재 프로젝트 폴더 책임과 구조`에 해당 폴더와 역할을 추가합니다.
- 기존 폴더에 현재 구조를 설명하는 데 중요한 파일이 추가되거나 대표 파일 구성이 바뀌면, `## 현재 프로젝트 폴더 책임과 구조`에 해당 폴더의 대표 파일 예시와 각 파일의 한 줄 역할을 실제 구조에 맞게 갱신한다.
