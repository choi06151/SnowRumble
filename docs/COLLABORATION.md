# Collaboration

## 목적

이 문서는 SnowRumble의 네 담당자와 각 담당자의 Codex가 함께 작업할 때 역할, 소유권, 공용 계약, 충돌 방지·대응과 인계 절차를 정의합니다.

## 세션 담당자

Codex는 세션의 첫 작업 전에 현재 대상 담당자를 확인합니다.

| 코드 | 담당자 | 역할 |
| --- | --- | --- |
| `S` | 서유정 | UI/UX, 그래픽 디자인, 레벨 디자인, 캐릭터·아이템 모델링 |
| `J` | 정다영 | 레벨 디자인 |
| `K` | 강혜원 | 서브 프로그래머, 멀티플레이와 아이템 기본 로직 |
| `C` | 최재원 | 메인 프로그래머, 멀티플레이 통합과 PvP·플레이어 |

- 사용자가 첫 요청에 담당자를 이미 명시했다면 다시 묻지 않습니다.
- 담당자가 확인되기 전에는 프로젝트 파일과 기준 문서를 수정하지 않습니다.
- Codex는 확인된 담당자의 사람 작업자와 같은 권한과 제한을 적용받습니다.
- 현재 세션 담당자가 바뀌면 변경 사실과 새 역할을 확인한 뒤 작업을 계속합니다.

## 역할별 기본 책임

### 서유정 (`S`)

- UI/UX 설계와 Widget Blueprint 구성
- UI 그래픽, 아이콘, 텍스트, UI 애니메이션
- 배정된 맵의 레벨 디자인과 표현 자산
- 캐릭터와 아이템 모델링, 머티리얼과 외형 표현
- 게임플레이 상태를 읽어 표현하되 서버 판정이나 복제 원본을 UI·모델 자산에서 변경하지 않음

### 정다영 (`J`)

- 배정된 맵의 레벨 디자인
- 맵 배치, 동선, 환경 구성과 맵 전용 표현 자산
- 배정된 `.umap`의 단독 수정
- 서버 판정이 필요한 환경 규칙은 로컬 Level Blueprint에서 확정하지 않고 프로그래머에게 공개 계약을 요청

### 강혜원 (`K`)

- 아이템의 기본 C++·Blueprint 로직
- 아이템 생성, 획득, 소유, 사용과 효과 적용의 멀티플레이 동작
- 아이템 내부 오류 수정과 아이템 담당 자산 연결
- 플레이어, PvP와 공용 경기 상태를 직접 수정하지 않고 공개된 계약을 사용
- 필요한 공용 플레이어·경기 API가 없으면 최재원에게 계약 변경을 요청

### 최재원 (`C`)

- 공용 네트워크 계약, 서버 권한과 복제 구조의 최종 검토
- PvP 모드, 라운드·매치 흐름과 승패
- 공용 플레이어 구조와 플레이어 기능
- 세션·로비와 공용 GameMode·GameState·PlayerState 계약
- 하네스, GDD, 전체 계획, Task 배정과 최종 통합
- 파트 간 충돌 시 소유권, 공용 계약과 병합 순서 결정

## 계획·Task 문서 수정 권한

- 각 담당자와 해당 Codex는 자기 `Tasks/{코드}/PLAN_{코드}.md`와 `Tasks/{코드}/`의 Task 문서를 작성·갱신할 수 있습니다.
- 개발자가 계획 문서를 직접 편집할 필요는 없으며, 대화에서 요청과 문제를 설명하면 Codex가 문서 변경을 담당합니다.
- 역할 내부 Task 순서·분할·오류 수정은 자기 계획에서 자율적으로 조정할 수 있습니다.
- `AGENTS.md`, `docs/`, 공통 템플릿, `Tasks/LEGACY_MIGRATION.md`와 중앙 `docs/PLANS.md`는 최재원(C)과 C Codex만 수정합니다.
- 비메인 Codex는 공용 변경이 필요하면 자기 계획의 `통합 변경 요청`에 기록하고 C에게 인계합니다.
- 문서 수정 권한은 코드·자산 소유권을 넓히지 않습니다.

## 세 가지 소유권

각 작업은 역할 이름만으로 배정하지 않고 아래 소유권을 구분합니다.

| 구분 | 책임 |
| --- | --- |
| 기능 소유자 | 기능 내부 구현, 오류 수정과 결과 인계 |
| 계약 소유자 | 다른 기능이 사용할 공개 API·이벤트·복제 상태의 설계와 변경 승인 |
| 자산 수정자 | 현재 Task에서 실제 파일·Blueprint·맵·자산을 수정하는 단독 담당자 |

- 하나의 기능에서 세 소유권을 한 사람이 모두 가질 수 있습니다.
- 기능 소유자와 계약 소유자가 다르면 기능 소유자는 공개 계약 안에서만 구현합니다.
- 자산 수정자는 `docs/PLANS.md`의 현재 작업 배정과 Task에 실제 경로 단위로 기록합니다.
- 현재 선점과 자산 수정자 기록이 파일명 이니셜보다 우선합니다.

## 공통 충돌 방지 규칙

1. 하나의 파일·Blueprint·맵·자산에는 동시에 한 명의 수정자만 둡니다.
2. 각 담당자는 별도 Git 브랜치와 별도 worktree 또는 별도 clone을 사용합니다.
3. Task 시작 전에 생성·변경 후보와 Unreal 자산을 실제 경로로 선점합니다.
4. 선점되지 않았거나 다른 담당자가 소유한 대상은 수정하지 않습니다.
5. 다른 파트의 변경이 필요하면 직접 수정하지 않고 필요한 공개 API, 이유와 호출 위치를 해당 소유자에게 요청합니다.
6. `.uasset`과 `.umap`은 자동 병합 가능한 텍스트로 간주하지 않습니다.
7. 하나의 `.umap`은 Task 기간 동안 한 명만 수정합니다. 두 레벨 담당자가 같은 맵을 동시에 수정하지 않습니다.
8. 공용 API의 시그니처·실행 위치·복제 방식을 바꾸기 전에는 영향받는 호출자와 자산을 기록하고 메인 프로그래머 승인을 받습니다.
9. 다른 담당자의 변경을 덮어쓰기, 되돌리기, 삭제, 이름 변경 또는 이동하지 않습니다.
10. 병합 전에는 코드뿐 아니라 Blueprint 부모, 이벤트, 프로퍼티 이름과 자산 참조 영향을 확인합니다.

## Git 브랜치 구조

| 브랜치 | 담당자 | 용도 |
| --- | --- | --- |
| `master` | 공용 통합 기준 | 검증된 공통 기준과 완료된 역할 브랜치 통합 |
| `C` | 최재원 | 공용 네트워크·PvP·플레이어·통합 준비 작업 |
| `K` | 강혜원 | 아이템 기본 로직 작업 |
| `S` | 서유정 | UI·아트·모델·눈숲속 작업 |
| `J` | 정다영 | 얼음 빙하·눈섬 레벨 작업 |

- 각 담당자는 자기 이니셜 브랜치에서만 일반 작업을 커밋합니다.
- `master`에는 기능을 직접 개발하지 않고, 결과 확인과 인계가 끝난 역할 브랜치만 아래 완료 작업 게시 절차로 통합합니다.
- 네 역할 브랜치는 같은 `master` 기준 커밋에서 시작합니다.
- 담당자별 별도 worktree 또는 clone에서 자기 브랜치를 checkout하여 작업합니다. 하나의 작업 폴더를 여러 담당자가 번갈아 쓰지 않습니다.
- 공유된 역할 브랜치의 이력을 강제로 다시 쓰지 않습니다. `push --force`, 공개 커밋의 rebase와 reset은 사용하지 않습니다.
- 최신 공통 기준이 필요하면 역할 브랜치에 `master`를 병합하고, 충돌은 이 문서의 충돌 절차와 자산 수정자 원칙에 따라 해결합니다.
- 다른 역할 브랜치를 자기 브랜치에 임의로 병합하지 않습니다. 파트 간 선행 결과는 실제 브랜치·커밋을 인계하고 최재원(C)가 병합 순서를 정합니다.
- 브랜치 이름은 담당자 코드와 동일한 대문자 `C`, `K`, `S`, `J`로 고정합니다.

### 작업 시작 자동 동기화

Codex는 세션 첫 작업, Task 시작·재개와 담당자 변경 시 개발자에게 Git 명령을 맡기지 않고 아래 절차를 먼저 수행합니다.

1. 현재 브랜치, upstream과 staged·tracked·untracked 변경을 확인합니다.
2. `git fetch origin --prune`으로 원격 상태를 갱신합니다.
3. 일반 작업은 확인된 담당자의 `C`, `K`, `S`, `J` 브랜치로 이동합니다. C의 명시적인 통합 작업에만 `master`를 사용합니다.
4. 변경 사항이 없어 안전할 때 Codex가 직접 담당 브랜치로 전환합니다.
5. 로컬이 원격보다 뒤에만 있고 작업 트리가 깨끗하면 `git pull --ff-only`를 자동 실행합니다.
6. 최신 상태이거나 로컬만 앞서 있으면 pull 없이 작업을 계속합니다.

다음 상황에서는 자동 동기화를 중단하고 상태를 사용자에게 보고합니다.

- 브랜치 전환 시 함께 이동하거나 충돌할 staged·tracked·untracked 변경이 있음
- 로컬과 원격 이력이 서로 갈라짐
- 예상한 원격 역할 브랜치 또는 upstream이 없음
- 네트워크·인증·fetch·pull 오류가 발생함

Codex는 동기화를 위해 임의 stash·commit·merge·rebase·reset·force-push를 하지 않습니다. 안전 여부를 확인할 수 없으면 프로젝트 파일 수정 전에 멈춥니다.

### 완료 작업 자동 게시

사용자가 작업 완료를 확인하고 push를 요청하면 해당 역할 Codex가 다음 Git 작업을 대신 수행합니다.

1. 현재 담당자·역할 브랜치와 완료 Task를 확인하고 필요한 검증, Task·PLAN 갱신과 인계를 마칩니다.
2. 원격을 다시 fetch하고 역할 브랜치와 `master`의 분기·충돌·공용 계약 승인 상태를 확인합니다.
3. 완료 Task가 소유한 파일과 필수 기록만 명시적으로 stage하고 Task 단위로 commit합니다. 관계없는 변경과 untracked 파일은 제외합니다.
4. 담당자의 `C`, `K`, `S`, `J` 브랜치에 push합니다.
5. 최신 `origin/master`를 기준으로 완료 커밋을 식별 가능한 merge commit으로 병합하고 필요한 통합 검증을 수행합니다.
6. 검증이 통과하면 `master`를 push하고, 담당 역할 브랜치도 새 master merge commit까지 안전하게 fast-forward하여 다시 push합니다.
7. 원래 담당 브랜치로 돌아와 역할 커밋·master 병합 커밋·검증·제외 파일을 보고합니다.

각 역할 Codex는 자기 역할의 완료 Task만 이 절차로 병합할 수 있습니다. 공용 계약·병합 순서에 미결정 사항이 있거나 다른 역할 소유 파일이 포함되면 최재원(C)의 결정을 받기 전 `master`에 병합하지 않습니다.

현재 작업 폴더에 관계없는 변경이 있으면 별도의 깨끗한 임시 worktree에서 master 통합을 진행합니다. 역할 브랜치 push 이후 master 충돌·검증 실패·동시 push 경쟁이 발생하면 역할 브랜치는 보존하고 master 병합만 보류합니다. 자동 충돌 해결, force-push, 임의 stash·reset은 하지 않습니다.

## 공용 계약 변경 절차

플레이어, PvP, 아이템, UI와 레벨이 함께 사용하는 상태나 API는 공용 계약으로 취급합니다.

1. 요청자가 필요한 동작, 데이터, 실행 위치와 사용 파트를 기록합니다.
2. 계약 소유자가 기존 공개 계약으로 해결할 수 있는지 확인합니다.
3. 새 계약이 필요하면 메인 프로그래머가 영향 범위와 구현 순서를 승인합니다.
4. 계약 소유자가 공개 API·이벤트·복제 상태를 먼저 구현합니다.
5. 기능 소유자가 자기 소유 범위에서 새 계약을 연결합니다.
6. 메인 프로그래머가 호스트·클라이언트 실행 위치와 통합 결과를 검토합니다.

기능 담당자가 공용 파일에 임시 코드를 먼저 추가하고 나중에 정리하는 방식은 사용하지 않습니다.

## 인계 규칙

파트 간 인계에는 아래 내용을 실제 이름으로 기록합니다.

- 제공하는 클래스·함수·이벤트·프로퍼티 또는 자산
- 로컬, 소유 클라이언트, 서버, 전체 클라이언트 중 실행 위치
- 호출 조건과 실패 조건
- 읽기 전용 상태와 변경 요청의 구분
- 선행 브랜치와 커밋
- 연결할 Blueprint·맵·UI·모델 자산
- 완료한 검증과 남은 결과 확인
- 병합 순서와 인계받는 담당자

## 충돌 발견 시 행동

1. 겹친 파일이나 자산의 수정만 즉시 중단합니다.
2. 자신의 브랜치 변경은 삭제하거나 되돌리지 않고 보존합니다.
3. 상대 변경을 임의로 병합·덮어쓰기·재생성하지 않습니다.
4. 아래 `협업 충돌 보고` 형식으로 메인 프로그래머에게 전달합니다.
5. 메인 프로그래머가 기능·계약·자산 소유자와 병합 순서를 다시 지정합니다.
6. 코드 충돌은 지정된 파일 소유자가 양쪽 요구사항을 확인해 해결합니다.
7. `.uasset`·`.umap` 충돌은 하나를 기준 자산으로 선택하고 다른 변경은 지정 담당자가 Unreal Editor에서 다시 적용합니다.
8. 해결과 결과 확인 전까지 관련 Task를 완료 처리하지 않습니다.

## 병합 원칙

- 사용자가 완료와 push를 명시한 자기 역할 Task는 해당 역할 Codex가 자동 게시할 수 있으며, 파트 간 충돌·공용 계약·병합 순서의 최종 결정은 최재원(C)에게 둡니다.
- 공용 계약을 먼저 반영하고 해당 계약을 사용하는 기능과 표현 자산을 뒤에 반영합니다.
- 서로 독립적인 맵과 자산은 파일 선점이 겹치지 않을 때 병렬 진행할 수 있습니다.
- 상대 작업을 받기 전에는 자신의 미완료 변경을 커밋하거나 안전하게 분리합니다.
- 메인 프로그래머는 다른 담당자의 내부 구현을 임의로 재작성하지 않고 계약, 검증, 충돌과 통합 결과를 중심으로 검토합니다.
- 병합 뒤 깨진 Blueprint 참조나 수동 재연결이 필요하면 해당 자산 수정자가 Unreal Editor에서 마무리합니다.

## 기존 파일과 역할별 Task

- 기존 파일은 담당자 이니셜을 붙이기 위해 일괄 이름 변경하지 않습니다.
- 기존 완료·진행중 Task는 당시 구현·검증 이력으로 보존합니다.
- 기존 Task의 새 기획 분류는 `Tasks/LEGACY_MIGRATION.md`를 기준으로 확인합니다.
- 새 작업은 `Tasks/C`, `Tasks/K`, `Tasks/S`, `Tasks/J`에서 시작하고 역할 내부 상태·순서는 각 `PLAN_*.md`, 파트 간 계약·선점·통합 상태는 `docs/PLANS.md`에서 갱신합니다.
- 기존 Task 파일의 완료·진행중 표시는 당시 이력으로 보존하며 새 역할별 Task 상태로 사용하지 않습니다.
