# Testing

## 목적

이 문서는 AI 에이전트가 코드 구현 후 검증하는 기준과 절차를 정의합니다.

## 검증 원칙

각 task 구현 후 아래 순서로 검증합니다.

1. 관련 코드 수정 완료 여부 확인
2. 현재 실행 확인 모드에 맞는 정적 점검 또는 로컬 실행 확인
3. `docs/STYLEGUIDE.md` 기준으로 Unreal C++/Blueprint/에셋 규칙 위반 여부 확인
4. 현재 task의 구현 범위와 완료 조건 일치 여부 확인
5. 진행 현황 문서 갱신

## 실행 확인 모드

현재 저장소의 기본 실행 확인 모드는 `수동 실행 확인`입니다. AI가 직접 에디터 실행과 인게임 확인까지 수행하면 토큰 소모가 크기 때문에 기본은 사람이 실행과 결과 확인을 담당합니다.

- `수동 실행 확인`: 에이전트는 코드와 설정을 준비하고, 사람은 실제 실행과 결과 확인을 담당합니다.
- `에이전트 확인`: 필요 시 에이전트가 로컬 실행 명령으로 에디터, 빌드, 또는 실행 동작을 확인합니다.

## 수동 실행 확인 모드

- 에이전트는 코드 눈검토, 관련 파일 점검, 기본 정적 확인(컴파일·빌드는 포함하지 않음), task 문서의 `수동 작업`과 `결과 확인` 절차 정리까지만 수행합니다.
- 사람은 코드 컴파일, Unreal Editor 실행, 맵 실행, PIE 또는 Standalone 실행, 입력 테스트, 기능 동작 확인처럼 실제 실행과 결과 확인을 수행합니다.
- 에이전트가 스스로 수행한 빌드·실행 결과는 확인 근거로 삼지 않으며, task 문서와 `docs/PLANS.md`에 확인 완료로 기록하지 않습니다.
- 수동 확인 항목은 현재 구현된 범위만 대상으로 삼습니다.
- 아직 연결되지 않은 다음 단계 기능을 현재 task 확인 항목에 섞지 않습니다.
- 실패 시 어떤 맵, 어떤 입력, 어떤 상태 변화, 어떤 UI 또는 애니메이션 반응이 문제인지 기록할 수 있어야 합니다.

## 멀티플레이 수동 확인 기준

네트워크 기능이 포함된 Task는 해당 Task에 필요한 범위에서 아래 항목을 결과 확인 절차에 포함합니다.

1. Listen Server 호스트와 최소 1개의 클라이언트를 실행합니다.
2. 호스트와 클라이언트 양쪽에서 참가와 기본 조작이 가능한지 확인합니다.
3. 한 플레이어가 만든 상태 변화가 필요한 다른 화면에도 동일하게 반영되는지 확인합니다.
4. 호스트 플레이어와 클라이언트 플레이어가 같은 규칙으로 판정되는지 확인합니다.
5. 중복 생성, 소유권 오류, 호스트 전용 동작, 클라이언트 전용 누락이 없는지 확인합니다.

지원 목표가 2~16명이라는 이유만으로 모든 Task에서 16개 클라이언트를 실행하지 않습니다. 기능 검증은 호스트 1명과 클라이언트 1명을 기본으로 하고, 인원 증가 검증은 통합·최종 검증 Task에서 수행합니다.

## SUB UI Task 확인 기준

- 연결된 Main Task가 완료되고 실제 UI 데이터·이벤트가 인계됐는지 확인합니다.
- SUB 프로그래머가 배정된 UI 자산만 수정했는지 확인합니다.
- 호스트와 클라이언트 각각에서 UI가 자신의 로컬 플레이어 상태를 표시하는지 확인합니다.
- UI가 서버 판정, RPC, 복제 프로퍼티와 게임플레이 상태를 직접 변경하지 않는지 확인합니다.
- UI 연결 문제로 C++ 또는 비UI Blueprint 변경이 필요하면 SUB Task에서 수정하지 않고 메인 프로그래머에게 반환합니다.

## 에이전트 확인 모드

- 사용자가 요청하거나 현재 저장소 흐름상 필요할 때만 로컬 실행 확인을 수행합니다.
- 실행 명령은 현재 저장소의 기존 Unreal 실행 방식과 빌드 구조를 우선 사용합니다.
